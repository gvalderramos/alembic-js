# 0007 - Test Assets

## Overview
Alembic-JS is tested with two kinds of files:

1. **Generated fixtures** (`test/fixtures/`, written by `tools/generate_fixtures.cpp`): tiny, deterministic files where every value is known, so tests can assert exact numbers. Each feature spec (0002–0006) extends this generator.
2. **Real-world resources** (`resource/`): files exported by DCC tools, which capture conventions and quirks the generator can't predict. Examples: Blender storing user properties as arrays, Bezier handles exported as control vertices, empty point clouds when every particle has died.

This spec defines what real-world coverage we need, how assets are created or sourced, licensing rules, and how they're stored and used in CI.

## Goals
- Every feature spec has at least one real-world file exercising it, in addition to its generated fixtures.
- Every committed asset has a known source and a redistributable license, recorded in `resource/README.md`.
- Assets are reproducible from scripts in this repo whenever possible.
- Large assets for benchmarks never bloat the git history.

## Sourcing Rules
1. **Prefer scripts.** Assets made by a script in this repo (`tools/blender/`, `tools/generate_fixtures.cpp`) are licensed with the repository and can be regenerated.
2. **Downloaded assets** need a license that allows redistribution and modification (CC0, CC-BY, MIT, BSD or similar). Record the URL, author, license and download date in `resource/README.md`. CC-BY requires attribution there.
3. **Contributed exports** (Houdini, Maya): the contributor states that they created the file and agrees to license it under the repository license. Record the tool and version.
4. **Never** commit assets from marketplaces or sites with "personal use only" or unclear terms.
5. The kettle's source and license must be confirmed. If they can't be, replace it with an equivalent generated asset.

## Storage
- Committed assets stay under ~2 MB each and ~10 MB in total. Mark `*.abc` as binary in `.gitattributes`, so Windows line-ending conversion never touches them.
- Large assets are git-ignored and produced on demand:
  - generated: `yarn assets:blender --large`;
  - downloaded: a future `scripts/fetch-assets.js` with a manifest (`resource/assets.json`: url, sha256, license, size). It verifies the checksum and caches under `.deps/assets/`.
- If committed assets outgrow the limits, move them to Git LFS or the fetch manifest. Don't rewrite history for files already committed.

## Tests Using Real-World Assets
- A new `test/resources.test.ts` runs smoke assertions per asset, kept loose so that re-exports with a newer Blender don't break them:
  - object types and counts, and expected paths;
  - sample counts and time range (30 fps: start 1/30 s);
  - meshes read at the first and last sample with consistent vertex and triangle counts;
  - topology changes in `changing_topology` (24 → 300 vertices);
  - the camera lens goes from 35 to 50 mm.
- As each feature spec lands, its tests add assertions on these assets. Examples: 0002 reads `particles` frames 35–40 as empty, and the `/Bezier` width mismatch doesn't throw; 0006 unwraps Blender's array-valued user properties.
- Benchmarks (`yarn bench`, not part of `yarn test`) use `large_mesh` when present and skip with a message otherwise.

## CI
- `yarn test` uses only committed assets, so CI needs no Blender and no network access.
- An optional weekly workflow (`assets.yml`) installs Blender, regenerates `resource/blender/`, and runs the resource tests against the fresh files. It catches exporter changes in new Blender versions without committing the regenerated files automatically.
- Benchmarks run in a separate, manually triggered workflow.

## Gaps Found While Building the Assets
- **Instancing:** `camera_rigid_instances.abc` is exported with Blender's instancing option, and the current reader shows the instances as normal objects. Alembic instancing (`IObject::isInstanceRoot()`, instance source paths) isn't exposed or spec'd. Users may want to know which objects share data, to create `InstancedMesh`es in three.js. Candidate for a follow-up spec.
- **Up axis:** Blender writes Y-up; Maya and Houdini are Y-up too. Some pipelines write Z-up, and Alembic has no standard up-axis metadata. Document this, and consider an `upAxis` option in the three.js bridge.
